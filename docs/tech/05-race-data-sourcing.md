## 1. 결론 요약

- **권장 방식: "공식 홈페이지 기준 관리자 입력 + 집계 사이트는 '발견용 신호'로만 쓰는 반자동 수집 + 주최사 셀프 등록"**
  - 집계 사이트(마라톤온라인 등)의 목록을 **통째로 복제하지 않는다.** 새 대회가 있는지 감지하는 데만 쓰고, 실제 저장하는 사실 정보는 **각 대회 공식 홈페이지에서 확인**해 관리자가 입력·승인한다.
  - 수집기는 "공식 홈페이지가 바뀌었는지" 감지해 **검수 대기열**에 올리는 역할만 한다. 자동으로 공개 데이터에 반영하지 않는다.
- **Phase 1 출시 목표: 출시일부터 6개월 안에 열리는 국내 도로 대회 중 하프·풀 종목이 있는 대회 전부 + 수도권 주요 10K 대회 → 약 120~200개** [추정, 기획 확정 필요]
- 공공 데이터에는 쓸 만한 대회 일정 데이터셋이 **없다** [확인]. 공개 API를 제공하는 집계 사이트도 찾지 못했다 [확인].

### 2.2 법적 검토 포인트 `[확인 필요]`

| 쟁점 | 내용 | 대응 |
|---|---|---|
| robots.txt | 법적 구속력은 약하지만 **위반 시 '권한 없는 접근' 판단에 불리**. 없으면 허용으로 보는 것이 관행 [추정] | 있으면 지킨다. 없어도 요청 간격 ≥ 10초, 명시적 User-Agent(`BeRunBot/1.0 (+연락처)`) |
| 저작권법 제93조 데이터베이스제작자 권리 | DB의 **전부 또는 상당한 부분**을 복제하면 침해. 개별 사실 소량은 해당 없지만, **반복·체계적으로 복제하면 상당한 부분으로 간주**될 수 있음 | 집계 사이트 DB를 복제하지 않는다. 대회 존재만 감지하고, 저장값은 공식 홈페이지에서 확인한 것만 |
| 부정경쟁방지법 제2조 제1호 (카)목 데이터 부정사용 | 업으로 제공되는 데이터를 부정하게 취득·사용 | 경쟁 앱(S3)은 수집하지 않는다 |
| 정보통신망법 | 접근 차단·우회 시 문제 | 로그인·차단 우회 금지 |
| 이미지·소개글 | 저작물 | 저장·노출 금지 (P-RACE-03). 링크만 |

참고 법령: 저작권법 <https://www.law.go.kr/법령/저작권법>, 부정경쟁방지 및 영업비밀보호에 관한 법률 <https://www.law.go.kr/법령/부정경쟁방지및영업비밀보호에관한법률>

## 3. 수집 방식 비교

| 기준 | A. 관리자 수동 입력 | B. 자동 수집기 + 수동 검수 | C. 주최사·플랫폼 제휴 |
|---|---|---|---|
| 초기 비용 | 낮음 (관리자 폼만) | 중간 (수집기 2~3주 개발 + 사이트별 파서) | 낮음(셀프 등록 폼) ~ 높음(API 연동) |
| 운영 비용 | **높음**: 대회당 입력 10~15분 [추정] → 200개 ≈ 40~50시간, 이후 주 10~20개 신규 + 변경 확인 | 중간: 파서 깨짐 대응, 검수 시간 (대회당 2~3분) | 낮음 (단, 영업·관계 유지 필요) |
| 정확도 | 높음 (공식 요강 확인 시) | 중간 → 검수 후 높음. 자동 반영 시 오류 위험 | **가장 높음** (주최사가 직접 입력) |
| 최신성 | 사람이 확인할 때만 | **높음** (변경 감지) | 주최사가 갱신할 때 |
| 커버리지 | 사람 시간에 비례 | 높음 | **초기에 매우 낮음** (협상력 없음) |
| 법적 위험 | 낮음 | 출처에 따라 다름: 공식 홈페이지 = 낮음, 집계 사이트 대량 복제 = **높음** | 가장 낮음 |
| 1인 운영 부담 | 출시 전 집중 부담 큼, 이후 꾸준한 반복 업무 | 개발 부담 + 깨짐 대응 | 영업 부담, 사용자가 모이기 전엔 효과 없음 |

## 4. 권장안: 단계별 계획

### Phase 1 출시 전 (개발 기간 병행, 약 3~4주)

1. **관리자 입력 도구 우선 (F-080)**: 대회·종목 입력 폼, 공식 URL 필수, "최종 확인일" 자동 기록, 중복 검사(대회명 + 날짜 + 지역).
2. **발견 목록**: 마라톤온라인 일정 목록에서 **대회명·날짜·공식 홈페이지 URL만** 하루 1회 읽어 "아직 등록 안 된 대회" 목록을 관리자에게 보여준다. 이 값은 공개 데이터로 저장하지 않고 검수 대기열(`race_candidates`)에만 둔다.
   - 운영자에게 이용 허락을 요청하는 메일을 보낸다 (허락받으면 출처로 표기, 거절하면 수동 발견으로 대체). `[확인 필요]`
3. **초기 데이터 입력 (D-014: 사용자가 관리자 웹으로 직접 입력)**: 범위(1장, 기획 PRD 2.2 "기준 목록")에 해당하는 대회를 **공식 홈페이지 요강 기준으로** 입력. 120~200개 × 10~15분 ≈ 25~50시간 [추정]. 큰 대회(서울마라톤, JTBC, 춘천, 경주 등)부터.
4. 출시 시 모든 대회에 출처(공식 홈페이지)와 최종 확인일 노출 (P-RACE-02), 오류 제보(F-016) 활성화.

### Phase 1 운영 (출시 후)

5. **변경 감지 수집기**: 등록된 대회의 공식 홈페이지 요강 페이지를 주 1회(접수 오픈 2주 전부터는 매일) 가져와 **본문 해시를 비교**한다. 바뀌면 검수 대기열에 올린다. 글·이미지는 저장하지 않고 해시와 추출한 사실 필드만 저장한다.
   - 사이트마다 구조가 달라 범용 파서는 비현실적이다. 처음엔 "바뀌었다"는 신호만 주고, 관리자가 보고 수정한다. 반복되는 플랫폼(같은 홈페이지 빌더·접수 대행사)이 보이면 그때 파서를 만든다.
6. **대회 상태 감시**: 대회일이 지났는데 `scheduled`이면 `finished`로 자동 전환 후보, 뉴스·공지에서 "취소/연기" 키워드를 찾으면 검수 대기열 (P-RACE-06).

### Phase 2 이후

7. **주최사 셀프 등록·수정 요청 폼** (웹): 주최사가 대회 정보·코스 GPX를 직접 올리고, 관리자가 승인한다. 삭제·수정 요청 3영업일 처리(P-RACE-04)도 이 경로로.
8. **제휴**: 사용자 수가 생긴 뒤 접수 대행·계측사(스마트칩 등)와 접수 오픈 정보, 결과 기록(Phase 4 F-05x) 연동을 제안한다. 기록 데이터는 제휴 없이 수집하지 않는다.

### 수집기 구현 원칙 (P-RACE-03 강제)
- 대상 도메인 허용 목록(allowlist) 방식. 경쟁 앱 도메인은 금지 목록에 넣는다.
- robots.txt 확인 후 요청, 도메인당 10초 이상 간격, 하루 1회 이하(변경 감시 제외), `BeRunBot` User-Agent에 연락처 명시.
- HTML 원문을 DB에 저장하지 않는다 (디버깅용 원문은 S3에 7일만 보관 [미정]).
- 수집 결과는 **절대 직접 공개 데이터(`races`)를 바꾸지 않는다.** 항상 `race_candidates` → 관리자 승인.
- 기술: 대부분 정적 HTML → `undici` + `cheerio`(+ EUC-KR은 `iconv-lite`). JS 렌더링이 필요한 사이트만 Playwright. BullMQ 스케줄 작업. (`02-tech-stack.md`의 "Playwright 기반 수집기"를 이렇게 조정 제안)

## 5. DB 스키마 검토 결과 (`04-db-schema.md` 3.3 수정)

기존 `races` / `race_events` / `race_sources` 로 **화면 표시에는 충분하지만, 검수 흐름과 변경 감지에는 부족**하다. 다음을 `04-db-schema.md`에 반영했다.

| 대상 | 변경 | 이유 |
|---|---|---|
| `races.publish_status` 추가 | `draft` / `published` / `hidden` | 검수 전 대회 비공개, 주최측 요청 시 숨김 (P-RACE-04). `status`(대회 진행 상태)와 분리 |
| `races.race_type` 추가 | `road` / `trail` / `ultra` / `track` / `virtual` | 필터·예측 대상 구분. Phase 1은 `road`만 게시 (D-013) |
| `races.registration_method` 추가 | `first_come` / `lottery` / `unknown` | 선착순 대회는 접수 오픈 알림(F-014)의 가치가 큼. 기획 확인 필요 |
| `races.dedupe_key` 추가 | 정규화한 대회명 + 날짜 (유니크 아님) | 같은 대회 중복 경고 (저장은 허용, PRD 8.4) |
| `race_events.registration_opens_at/closes_at` 추가 (nullable) | 종목별 접수 기간이 다른 경우만 사용 | 일부 대회는 풀코스만 먼저 접수 [추정] |
| `race_sources` 확장 | `source_kind`, `external_id`, `content_hash`, `last_checked_at`, `last_changed_at`, `is_primary` | 변경 감지, "출처" 표시에 쓸 대표 출처 지정 |
| **`race_candidates` 신규** | 수집기·제보·주최사가 올린 신규/변경 후보와 검수 결과 | 수집 결과가 공개 데이터를 바로 바꾸지 않게 하는 완충 지대 |
| `race_reports`와의 관계 | 유지. 관리자가 제보를 반영할 때 `race_candidates`로 옮기지 않고 직접 수정 | 사용자 제보는 개수가 적어 별도 대기열 불필요 |
