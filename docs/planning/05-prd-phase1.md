## 3. 공통 규칙

### 3.1 시간·날짜
- 모든 시각은 **한국 표준시(Asia/Seoul)** 기준으로 계산·표시한다. "오늘", "D-day", "N일 전"은 KST 날짜 기준이다.
- D-day 표기: 대회일 당일 = `D-DAY`, 하루 전 = `D-1`, 지난 대회 = 표시하지 않음 (`종료` 배지).
- 날짜 표기: `2026.11.08 (일)`. 시각 표기: `08:00` (24시간제).

### 3.2 기록·페이스 표기
| 대상 | 형식 | 예 |
|---|---|---|
| 기록 (1시간 이상) | `h:mm:ss` | `1:58:30` |
| 기록 (1시간 미만) | `mm:ss` | `55:00` |
| 페이스 | `m'ss"/km` | `5'38"/km` |
| 거리 | 5K / 10K / 하프 / 풀 / `12.5km` | |

- 페이스(초/km) = `round(기록초 ÷ (거리m ÷ 1000))`. 저장값도 정수 초.
- 표준 거리: 5K = 5,000m, 10K = 10,000m, 하프 = 21,097m, 풀 = 42,195m.

### 3.3 거리 분류 (distance_category)
기록과 종목 모두 아래 분류를 쓴다. 종목은 관리자가 분류를 직접 고른다 (A-003, 거리로 자동 제안). (DB 추가 제안: `race_events.category`)

| 분류 | 값 | 기록 입력 시 거리 | 종목 자동 제안 기준 (관리자 수정 가능) |
|---|---|---|---|
| 5K | `5k` | 5,000m 고정 | 4,500 ~ 5,500m |
| 10K | `10k` | 10,000m 고정 | 9,500 ~ 10,500m |
| 하프 | `half` | 21,097m 고정 | 21,000 ~ 21,200m |
| 풀 | `full` | 42,195m 고정 | 42,000 ~ 42,300m |
| 기타 | `other` | 1.0 ~ 100.0km, 0.1km 단위 직접 입력 | 그 외 전부 |

### 3.4 공통 상태 처리
| 상황 | 처리 |
|---|---|
| 최초 로딩 | 화면 구조를 유지한 스켈레톤 표시. 스피너만 단독으로 쓰지 않는다. |
| 당겨서 새로고침 | 목록 화면(S-010, S-011, S-020, S-030, S-061) 모두 지원 |
| 네트워크 끊김 (최초 로딩 실패) | 전체 화면 에러: "인터넷 연결을 확인해주세요" + [다시 시도]. 캐시가 있으면 캐시를 보여주고 상단에 "오프라인 상태예요. 최신 정보가 아닐 수 있어요" 배너 |
| 네트워크 끊김 (저장 동작 중) | 입력값 유지, 토스트 "저장하지 못했어요. 다시 시도해주세요" |
| 서버 오류 (5xx) | 전체 화면: "잠시 문제가 생겼어요" + [다시 시도]. 저장 동작은 토스트 |
| 인증 만료 (401) | refresh token으로 1회 재발급 시도 → 실패하면 S-002로 이동, 토스트 "다시 로그인해주세요" |
| 삭제된 리소스 (404) | "삭제되었거나 찾을 수 없는 정보예요" + [뒤로] |
| 중복 탭 | 저장·등록 버튼은 요청 중 비활성화 (스피너 표시) |
| 오프라인 캐시 | 대회 목록·상세, 내 대회, 내 기록은 마지막 조회 결과를 기기에 캐시한다 (최대 7일) |

### 3.5 입력값 공통 규칙
- 앞뒤 공백은 제거한 뒤 검증한다. 글자 수는 **문자(코드포인트) 단위**로 센다 (한글 1자 = 1).
- 검증 실패 메시지는 입력란 바로 아래에 빨간 글씨로 표시하고, 저장 버튼은 모든 필수값이 유효할 때만 활성화한다.
- **서버도 같은 규칙으로 다시 검증한다** (클라이언트 검증은 안내용, 04 문서 원칙). 검증 스키마는 Zod로 앱·서버가 공유한다 (tech/02).

### 3.6 외부 링크
- 공식 홈페이지·접수 링크는 **인앱 브라우저**(iOS SFSafariViewController, Android Custom Tabs)로 연다.
- `https://`가 아닌 링크는 관리자 단계에서 저장할 수 없다 (8장).

## 4. 기능 상세

### 4.1 F-001 소셜 로그인

**사용자 스토리**
- 러너로서, 비밀번호를 만들지 않고 평소 쓰는 카카오·Apple·Google 계정으로 1분 안에 가입하고 싶다.

**상세 동작**
1. S-002에 로그인 버튼을 노출한다.
   - iOS: 카카오 → Apple → Google 순
   - Android: 카카오 → Google 순 (Apple 로그인은 Phase 1 Android에서 제공하지 않는다 — D-016 확정. iPhone에서 Apple로 가입한 사용자는 Android에서 로그인할 수 없으며, 소셜 계정 연동 추가 기능과 함께 Phase 2 이후 검토)
2. 소셜 SDK 인증 성공 → 서버에 provider 토큰 전달 → 서버가 provider에 검증한다.
3. `(provider, provider_uid)`가 이미 있으면 **로그인**: JWT 발급 (access 15분, refresh 30일, tech/03) → S-001 라우팅 규칙(6.1)에 따라 이동.
4. 없으면 **가입 진행**: 서버는 `users` 행을 아직 만들지 않고 **가입용 임시 토큰(유효 30분)** 을 발급한다 → S-003 → S-004. 토큰 내용(provider, provider_uid, 이메일)은 서버 임시 저장소(30분 후 자동 삭제)에만 두고 앱에는 랜덤 토큰만 준다. 가입이 중단되거나(만 14세 미만, 사용자 이탈) 30분이 지나면 서버가 **카카오 연결 끊기(unlink)·Apple 토큰 revoke를 호출**해 소셜 쪽 연결도 남기지 않는다 (카카오는 우리 서버가 토큰을 검증하는 순간 연결된 것으로 보기 때문). 사용자에게 보이는 변화는 없다. `users`·`auth_identities`·`user_profiles`·`privacy_settings`·`notification_settings`·`user_consents`는 **S-004 완료 시 한 트랜잭션으로 생성**한다. (만 14세 미만의 개인정보를 서버에 남기지 않기 위해서다.)
5. 이메일은 provider가 주면 저장하고 주지 않으면 비워 둔다 (카카오는 선택 동의일 수 있음). 이메일은 필수가 아니다.
6. 같은 이메일이라도 provider가 다르면 **별도 계정**이다. Phase 1에서는 자동 병합·연동 추가를 하지 않는다 (9장).

**예외·에러**
| 상황 | 처리 |
|---|---|
| 사용자가 소셜 인증 창을 닫음 | S-002 유지, 메시지 없음 |
| provider 오류·토큰 검증 실패 | 토스트 "로그인하지 못했어요. 다시 시도해주세요" |
| 가입 임시 토큰 만료 (30분 경과) | S-002로 돌아가고 토스트 "시간이 지나 처음부터 다시 진행해주세요" |
| 계정 상태 `suspended` | 로그인 거부, 안내 화면 "이용이 제한된 계정이에요. 문의: {고객센터 이메일}" |
| 계정 상태 `dormant` (휴면, P-RET-03) | 로그인을 막지 않는다. 소셜 로그인 성공 = 본인 확인으로 보고 **추가 본인 확인 없이** `active`로 되돌린 뒤 **휴면 해제 안내 화면**을 1회 보여준다 (아래 "휴면 해제") |
| 탈퇴 후 같은 소셜 계정으로 재가입 | 신규 가입으로 처리 (4.15 참고) |

**휴면 해제** (P-RET-03)
- 대상: **1년 이상 접속(앱 사용)하지 않아** `dormant`가 된 계정. "접속" = 소셜 로그인·가입·앱을 열 때의 토큰 재발급(회전) 중 **마지막 시각**. 앱은 refresh token으로 로그인을 유지하므로 소셜 로그인만 세면 매일 쓰는 사용자도 휴면이 되기 때문이다.
- 휴면 전환 30일 전에 **N-09 휴면 안내**(앱 푸시 + 앱 내 알림)를 보낸다 (7.2). **이메일 안내는 보류** (D-021 — 출시 후 첫 휴면 대상이 생기기 전에 발송 서비스·발신 주소와 함께 결정). 안내 없이 휴면으로 바꾸지 않는다: 안내가 늦게 나가면(배치 장애 등) 휴면 전환일도 **안내 발송일 + 30일**로 미룬다.
- 안내를 받은 뒤 휴면 전환일 전에 앱을 열면(접속) 휴면 전환은 취소되고 기준일이 다시 계산된다.
- 흐름: S-002 소셜 로그인 → 서버가 `active`로 되돌리고 로그인 응답에 휴면 해제 여부를 표시 → S-001 라우팅 규칙대로 필수 약관 재동의(필요 시) → **휴면 해제 안내 화면** → S-010.
- 안내 화면 (S-002의 하위 화면, 화면 수 미포함): 제목 "다시 만나서 반가워요, {닉네임}님" / 본문 "1년 넘게 접속하지 않아 휴면 상태였던 계정을 다시 사용할 수 있게 했어요. 기록과 관심 대회는 그대로 있어요." / 한 줄 안내 "알림 설정을 확인해주세요" + [알림 설정 보기] → S-064 / 주 버튼 [시작하기] → S-010. 닫기·뒤로 = [시작하기].
- 휴면 기간에 지나간 대회는 평소처럼 "지난 대회"로 보인다. 알림 설정·마케팅 동의는 휴면 전 값 그대로다 (휴면 중에는 서비스·마케팅 푸시를 보내지 않았으므로, P-RET-03).
- 휴면 계정의 데이터를 분리 보관했다면 로그인 시 복원한다. 분리 보관 의무와 방식은 `[확인 필요]` (P-RET-03).

**수용 기준**
- Given 신규 사용자, When 카카오 로그인 성공, Then S-003 약관 동의 화면이 열린다.
- Given `dormant` 계정, When 같은 소셜 계정으로 로그인, Then 계정이 `active`가 되고 휴면 해제 안내 화면이 1회 뜬 뒤 [시작하기]로 S-010이 열린다.
- Given 휴면 해제 직후 다시 로그인, Then 안내 화면이 뜨지 않는다.
- Given 기존 사용자, When 같은 provider로 로그인, Then 약관·프로필 화면 없이 S-010 홈이 열린다.
- Given iOS 기기, When S-002를 열면, Then Apple 로그인 버튼이 다른 소셜 버튼과 동등한 크기로 보인다.
- Given 신규 사용자가 S-003에서 앱을 종료, When 다시 로그인, Then 서버에 `users` 행이 없으므로 S-003부터 다시 진행한다.
- 로그인 시작부터 S-004 완료까지 중앙값 60초 이내 (S-005, S-006 제외).

### 4.2 F-002 약관·개인정보 동의

**사용자 스토리**
- 러너로서, 무엇에 동의하는지 알고 필요한 것만 동의하고 싶다.

**동의 항목 (Phase 1)**
| 항목 | `terms_versions.kind` | 필수 | 비고 |
|---|---|---|---|
| 서비스 이용약관 | `service` | 필수 | |
| 개인정보 수집·이용 동의 | `privacy` | 필수 | 수집 항목·목적·보존 기간 요약 표를 화면에 함께 표시 |
| 마케팅 정보 수신 동의 (앱 푸시) | `marketing` | 선택 | 동의하면 `notification_settings.marketing = true` |

- 위치기반서비스 이용약관은 Phase 3에서 받는다 (Phase 1에 노출하지 않음). 야간 마케팅 수신 동의(`night_push`)는 Phase 1에서 받지 않는다 — Phase 1은 야간(21:00~08:00)에 마케팅 푸시를 아예 보내지 않는다 (P-NOTI-02).
- 개인정보 처리방침은 동의 대상이 아니라 **게시 대상**이다. S-003 하단에 "개인정보 처리방침 보기" 링크를 둔다. 주소는 **원격 설정**(`GET /app-config`의 `privacyPolicyUrl`, 관리자 owner가 `app_configs`에서 수정)에서 받는다 — 도메인(Q-12)이 정해지기 전에도 임시 게시 주소로 바꿔 끼울 수 있고, 개정 시 앱 배포 없이 바꿀 수 있다. S-065의 "개인정보 처리방침" 행도 같은 주소. 값이 비어 있으면(개발 환경) 링크를 숨기지 않고 "개인정보 수집·이용 동의" 전문을 대신 연다. **운영 환경 출시 전에 반드시 값을 넣는다** (P-LEGAL 체크리스트).

**상세 동작**
1. [전체 동의] 체크 = 필수 + 선택 모두 체크. 하나라도 해제하면 전체 동의 체크가 풀린다.
2. 각 항목 오른쪽 [보기] → 약관 전문을 웹뷰로 연다 (`terms_versions.content_url`).
3. 필수 2개가 체크되어야 [다음]이 활성화된다.
4. 동의 기록은 S-004 완료 시 `user_consents`에 `agree` 행으로 저장한다 (항목별 1행, 약관 버전 포함). 선택 항목을 체크하지 않았으면 행을 만들지 않는다.
5. 마케팅 동의 시 가입 완료 직후 토스트: "{YYYY.MM.DD} 마케팅 정보 수신에 동의했어요" (수신 동의 처리 결과 고지 `[확인 필요]`).

**약관 개정 시 재동의**
- 필수 약관의 새 버전이 `effective_at`에 도달하면, 기존 사용자가 다음에 앱을 열 때 S-001에서 **재동의 화면**(S-003과 같은 레이아웃, 변경된 항목만, 상단에 "약관이 변경되었어요" + 주요 변경 요약)을 띄운다. 동의하기 전에는 다른 화면으로 갈 수 없다. [동의하지 않음]을 누르면 "동의하지 않으면 서비스를 이용할 수 없어요. 탈퇴하시겠어요?" → [탈퇴 안내 보기](S-066) / [돌아가기].
- 개정 사전 공지(시행 7일 전, 불리한 변경은 30일 전)는 A-008 공지로 한다 `[확인 필요]`.

**수용 기준**
- Given S-003, When 필수 1개만 체크, Then [다음]이 비활성 상태다.
- Given 전체 동의 체크 상태, When 마케팅 항목만 해제, Then 전체 동의 체크가 풀리고 [다음]은 활성 상태를 유지한다.
- Given 가입 완료, Then `user_consents`에 service·privacy `agree` 행이 각 1개, 약관 버전 id와 함께 존재한다.
- Given 필수 약관 새 버전이 시행됨, When 기존 사용자가 앱을 열면, Then 재동의 화면이 먼저 뜨고 동의 전에는 홈으로 갈 수 없다.

### 4.3 F-003 러너 프로필

**사용자 스토리**
- 러너로서, 최소한의 정보만 입력하고 내 지역 대회를 추천받고 싶다.

**입력 항목과 검증**
| 항목 | 필수 | 입력 방식 | 검증 규칙 | 저장 위치 |
|---|---|---|---|---|
| 닉네임 | 필수 | 텍스트 | 2~12자. 허용 문자: 한글 완성형, 영문 대소문자, 숫자, `_`, `.`. 공백 불가. 대소문자 무시하고 중복 불가. 금칙어·예약어 불가 (아래) | `user_profiles.nickname` |
| 출생연도 | 필수 | 연도 선택 (휠) | 1926 ~ 올해. 만 14세 판정 (아래) | `users.birth_year` |
| 지역 | 필수 | 시·도 17개 중 1개 | 목록 값만 | `user_profiles.region_code` |
| 성별 | 선택 | 남성 / 여성 / 선택 안 함 (기본: 선택 안 함) | — | `user_profiles.gender` |
| 러닝 시작 연도 | 선택 | 연도 선택: 올해 ~ 1950, "선택 안 함" | 출생연도 + 5 이상 | `user_profiles.running_since` |

- **닉네임 금칙어·예약어**: 운영자가 관리하는 목록과 부분 일치하면 불가. 초기 예약어: `berun`, `비런`, `admin`, `관리자`, `운영자`, `운영진`, `공식`, `official`, `staff`. 욕설 목록은 서버 설정 파일로 관리한다 (관리자 UI는 Phase 2).
- **닉네임 중복 확인**: 입력 멈춘 뒤 500ms 후 자동 확인. 결과: "사용할 수 있어요"(초록) / "이미 사용 중이에요" / "사용할 수 없는 닉네임이에요"(금칙어). 저장 시 서버가 다시 확인하고 그 사이 선점되면 "이미 사용 중이에요"를 띄운다.
- **만 14세 판정** (P-ACC-01, 연도만 받기 때문에):
  - `올해 − 출생연도 ≥ 15` → 통과
  - `올해 − 출생연도 ≤ 13` → 가입 중단
  - `올해 − 출생연도 = 14` → 추가 질문 "올해 생일이 지났나요?" [지났어요] → 통과 / [아직이에요] → 가입 중단. **답은 저장하지 않는다.**
  - 가입 중단 화면: "BeRun은 만 14세 이상부터 이용할 수 있어요." + [확인] → 앱 첫 화면(S-002). 서버에 아무 정보도 남기지 않고, 기기에 24시간 동안 가입 재시도 차단 플래그만 둔다. 차단 중 로그인 시도 시 같은 안내를 다시 띄운다.
  - 이 방식(자기 신고 + 연도)이 법적으로 충분한지 `[확인 필요]` (11장 Q-01).
- 프로필 사진·자기소개·공개 범위 설정은 Phase 1에 없다 (Phase 1에는 다른 사용자가 내 프로필을 보는 기능이 없음). `privacy_settings`는 DB 기본값으로 생성만 한다.

**수정 (S-062)**
- 닉네임: 마지막 변경 후 **7일이 지나야** 다시 바꿀 수 있다. 바꿀 수 없으면 입력란 아래 "{M월 D일}부터 바꿀 수 있어요". (DB 추가 제안: `user_profiles.nickname_changed_at`)
- 출생연도: Phase 1에서는 **수정 불가** (연령 확인 우회 방지). 화면에 회색으로 표시하고 "출생연도는 바꿀 수 없어요. 잘못 입력했다면 고객센터로 문의해주세요".
- 지역·성별·러닝 시작 연도: 언제든 수정.

**수용 기준**
- Given 2026년, When 출생연도 2013 선택(13세), Then 가입 중단 화면이 뜨고 서버에 `users` 행이 생기지 않는다.
- Given 2026년, When 출생연도 2012 선택(차이 14), Then "올해 생일이 지났나요?" 질문이 뜬다.
- Given 닉네임 "러너" 사용 중, When "러너" 입력, Then "이미 사용 중이에요"가 뜨고 [완료]가 비활성이다.
- Given 닉네임 "BeRun_kim", Then 예약어 부분 일치로 "사용할 수 없는 닉네임이에요".
- Given 닉네임 "Runner"가 있고 "runner" 입력, Then 중복으로 판정한다.

### 4.4 F-004 최근 기록 입력

**사용자 스토리**
- 러너로서, 내가 뛴 대회·훈련 기록을 몇 초 만에 넣고 이것으로 예상 기록을 받고 싶다.

**입력 항목과 검증**
| 항목 | 필수 | 입력 방식 | 검증 규칙 |
|---|---|---|---|
| 거리 | 필수 | 칩: 5K / 10K / 하프 / 풀 / 기타 | 기타는 1.0 ~ 100.0km, 소수점 첫째 자리까지 |
| 기록 | 필수 | 시·분·초 3칸 숫자 | 시 0~23, 분 0~59, 초 0~59, 0초 불가. **페이스 2'30"~20'00"/km 범위** 밖이면 "기록을 다시 확인해주세요" (예: 10K 20:00 미만 또는 3:20:00 초과) |
| 날짜 | 필수 | 달력 피커 + 빠른 선택 칩 [오늘] [어제] | 1990-01-01 ~ 오늘. 미래 날짜는 달력에서 비활성. (웹 미리보기 빌드는 `YYYY-MM-DD` 직접 입력 + [오늘]·[어제]로 대신해도 된다 — 확인용, 제품 사양 아님) |
| 구분 | 필수 | 대회 / 개인 훈련 (기본: 대회) | `run_records.kind` = `race` / `training` |
| 제목 | 선택 | 텍스트 | 0~40자. 예: "2026 JTBC 마라톤" |

- 한 사용자당 기록 최대 **500개**. 초과 시 "기록은 500개까지 저장할 수 있어요".
- 같은 날짜·같은 거리·같은 기록이 이미 있으면 저장 전에 "같은 기록이 이미 있어요. 그래도 저장할까요?" [저장] / [취소]. **추가와 수정 모두** 확인한다. 수정은 날짜·거리·기록 중 하나라도 바뀌었고, 바뀐 결과가 **자기 자신이 아닌** 다른 기록과 같을 때만 묻는다 (제목·구분만 바꾸면 묻지 않음).
- 기록 저장·수정·삭제는 기존 예측(`predictions`)을 다시 계산하지 않는다 (예측은 그 시점 스냅샷). 대신 S-030 "최근 예측"에 "기록이 바뀌었어요 · 다시 예측" 표시 (6.12).
- 예측에 쓰이는 기록 조건(최근 365일, 3~42.195km)은 5장. 조건 밖 기록도 저장은 된다. 기록 목록에서 예측 제외 기록은 "예측 미사용" 회색 태그를 단다 (365일 초과, 3km 미만, 42.195km 초과).

**수용 기준**
- Given 10K, When 기록 0:18:00 입력 (1'48"/km), Then "기록을 다시 확인해주세요"가 뜨고 저장할 수 없다.
- Given 기타, When 거리 0.5 입력, Then "1.0~100.0km 사이로 입력해주세요".
- Given 날짜에 내일 선택 시도, Then 선택할 수 없다 (달력에서 비활성).
- Given 기록 저장 성공, Then S-030 목록 맨 위(날짜 최신순)에 나타난다.
- Given 기록 A를 수정해 날짜·거리·기록이 기록 B와 같아짐, Then "같은 기록이 이미 있어요. 그래도 저장할까요?"가 뜬다.
- Given 기록 A의 제목만 수정, Then 중복 확인 없이 저장된다.

### 4.5 F-010 대회 목록·캘린더 보기

**사용자 스토리**
- 러너로서, 앞으로 열리는 대회를 날짜순으로 훑어보고 달력으로 주말별 대회를 보고 싶다.

**상세 동작**
- 노출 대상: 관리자가 **게시** 상태로 둔 대회만 (`races.publish_status = published`, tech/05 제안). `draft`(검수 전)·`hidden`(주최 측 요청 등)은 앱에 보이지 않는다.
- Phase 1 대회 종류는 **도로 대회(`race_type = road`)만** 게시한다. 트레일·울트라·트랙·온라인(버추얼) 대회는 등록하지 않는다 (9장).
- 기본 보기: **리스트**. 우측 상단 토글로 캘린더 ↔ 리스트 전환, 마지막 선택을 기기에 저장한다.
- 기본 조건: `race_date ≥ 오늘`, 취소·연기 대회 포함(배지로 표시), 정렬은 대회일 오름차순 → 같은 날은 대회명 가나다순.
- 페이지: 20개씩 무한 스크롤.
- **리스트 카드**: 대회명(최대 2줄, 넘치면 말줄임), 대회일·요일, 지역(시·도), 종목 칩(5K/10K/하프/풀/기타 — 분류 순서대로, 중복 제거), 접수 상태 배지, 접수 방식 배지(`선착순` / `추첨`, 모르면 표시 안 함 — `races.registration_method`), D-day(30일 이내만), 관심 하트 버튼.
- 리스트는 **월별 헤더**("2026년 11월")로 묶는다.
- **캘린더**: 월간 달력. 대회가 있는 날에 점과 개수(1~9, 10 이상은 "9+"). 날짜를 누르면 달력 아래에 그날 대회 리스트 카드. 기본 선택일은 오늘. 좌우 스와이프로 월 이동 (오늘 기준 −1개월 ~ +12개월). 필터가 적용되면 캘린더 점도 필터 결과만 센다.
  - **지난 날짜**(오늘 이전, 이번 달 앞부분과 지난달): "종료 포함" 필터와 **상관없이** 점·개수를 보여주고, 날짜를 누르면 그날의 지난 대회 목록(`종료` 배지)도 보여준다. 달력에서 지난 날짜가 비어 있으면 "대회가 없었던 날"로 오해되기 때문이다. 지난 날짜의 점·개수는 회색으로 흐리게 표시해 앞으로 열릴 대회와 구분한다.
  - **숫자와 목록이 항상 같도록**: 캘린더 보기에서는 앱이 달력 요청(`GET /races/calendar`)과 날짜 목록 요청(`GET /races?date=`) **둘 다** `includeEnded=true`로 보낸다. 다른 필터(지역·거리·접수 상태·참가비·취소 숨기기)는 두 요청에 똑같이 적용한다.
  - 리스트 보기와 검색은 지금처럼 "종료 포함" 토글을 따른다 (기본: 지난 대회 제외).

**접수 상태 계산 (서버 계산, 저장하지 않음)**
| 우선 | 조건 | 배지 |
|---|---|---|
| 1 | `races.status = cancelled` | `취소` (회색) |
| 2 | `race_date < 오늘` 또는 `status = finished` | `종료` (회색) |
| 3 | `registration_opens_at`이 없음 | `접수 일정 미정` |
| 4 | 지금 < `registration_opens_at` | `접수 예정` (파랑) + 7일 이내면 "D-n" |
| 5 | `opens_at ≤ 지금 < registration_closes_at` (closes_at 없으면 대회 전날까지) | `접수 중` (초록) |
| 6 | 지금 ≥ `registration_closes_at` | `접수 마감` (회색) |
| 추가 | `status = postponed` | 위 배지 옆에 `연기` 배지를 함께 표시 |

**빈 상태·에러**
- 조건에 맞는 대회 없음: "조건에 맞는 대회가 없어요" + [필터 초기화] (필터 사용 시) / "등록된 대회가 없어요" (필터 없음).
- 캘린더에서 선택한 날 대회 없음: "이 날은 대회가 없어요".

**수용 기준**
- Given 오늘 2026-10-21, Then 리스트 첫 카드는 대회일이 2026-10-21 이후 중 가장 빠른 대회다.
- Given 지난 대회, Then 기본 리스트에 보이지 않는다 (필터 "종료 포함"을 켜야 보인다).
- Given 취소된 대회, Then 리스트에 남아 있고 `취소` 배지가 붙는다.
- Given 관리자가 초안으로 저장한 대회, Then 앱 어디에도 노출되지 않는다.

### 4.6 F-011 대회 검색·필터

**사용자 스토리**
- 러너로서, "서울·경기, 다음 달, 하프"처럼 조건을 걸어 나에게 맞는 대회만 보고 싶다.

**검색**
- 대상: 대회명, 장소명, 주최. 부분 일치, 공백 무시, 대소문자 무시.
- 입력: 1~30자. 1자 이상 입력 후 300ms 멈추면 검색한다. 31자 이상 입력 불가.
- 최근 검색어: 기기에 최대 10개 저장, 개별 삭제·전체 삭제.
- 검색 결과에는 지난 대회도 포함하되 맨 아래에 "지난 대회" 구분선으로 분리한다.

**필터**
| 필터 | 선택 | 기본값 |
|---|---|---|
| 지역 | 시·도 17개 다중 선택 | 전체 |
| 기간 | 이번 달 / 다음 달 / 3개월 이내 / 직접 선택(시작일~종료일, 최대 12개월 범위) | 전체 (오늘 이후) |
| 거리 | 5K / 10K / 하프 / 풀 / 기타 다중 선택 (종목 하나라도 해당하면 포함) | 전체 |
| 접수 상태 | 접수 예정 / 접수 중 / 접수 마감 / 접수 일정 미정 다중 선택 | 전체 |
| 참가비 | 3만 원 이하(≤ 30,000원) / 3~5만 원(30,001~50,000원) / 5~10만 원(50,001~100,000원) / 10만 원 초과(> 100,000원) 다중 선택. **경계값은 낮은 구간에 포함**한다 (30,000원 = "3만 원 이하", 50,000원 = "3~5만 원", 100,000원 = "5~10만 원"). 종목 중 하나라도 해당하면 포함. 무료(0원)는 "3만 원 이하" | 전체 |
| 종료 포함 | 토글 — **리스트 보기에만 적용** (캘린더는 지난 날짜도 항상 표시, 4.5). 필터 시트에서 토글 아래 회색 안내 "캘린더는 지난 날짜도 함께 보여요" | 끔 |
| 취소 대회 숨기기 | 토글 | 끔 |

- 난이도 필터는 Phase 1에서 **제외**한다 (코스 데이터가 Phase 2). 02 문서 요약표에서 제거했다.
- 필터 시트 하단 버튼에 결과 수를 실시간 표시: "128개 대회 보기". 0개면 버튼 비활성 + "조건에 맞는 대회가 없어요".
- 적용된 필터는 S-020 상단에 칩으로 보이고, 칩의 ×로 하나씩 해제한다. [초기화]는 전부 해제.
- 필터 상태는 기기에 저장해 앱을 다시 열어도 유지한다.
- 참가비가 없는(미입력) 종목은 참가비 필터를 걸면 제외된다.

**수용 기준**
- Given 지역=서울, 거리=하프, When 적용, Then 서울에서 열리고 하프 종목이 하나 이상 있는 대회만 나온다.
- Given 검색어 "춘천", Then 대회명·장소·주최에 "춘천"이 들어간 대회가 나온다.
- Given 필터 적용 후 앱 재시작, Then 같은 필터가 유지된다.

### 4.7 F-012 대회 상세

**사용자 스토리**
- 러너로서, 대회 일정·종목·참가비·접수 기간을 한 화면에서 확인하고 공식 접수 페이지로 바로 가고 싶다.

**표시 항목** — 값이 없을 때: 참가비·출발 시각·제한 시간·접수 기간은 **"미정 · 공식 홈페이지 확인"** 으로 표시하고, 주최·장소 주소·정원·코스 링크는 행을 숨긴다. 출처·최종 확인일은 항상 표시.
| 구역 | 항목 |
|---|---|
| 헤더 | 대회명, 상태 배지(접수 상태 + 취소/연기), D-day |
| 기본 정보 | 대회일·요일, 가장 이른 출발 시각, 장소명·주소 (DB 추가 제안: `races.venue_address`), 지역, 주최 |
| 대회장 위치 (지도) | **앱 내 네이버 지도** (D-008). 상세 동작은 아래 "대회장 위치 지도" |
| 접수 | **참가 예정이면 맨 위에 내 참가 예정 카드** — "{종목} · 목표 {기록}" + 접수 상태 배지 + [변경] (4.10.1). 그 아래 접수 방식(선착순 / 추첨, 모르면 숨김), 접수 기간 `2026.08.01 (금) 10:00 ~ 2026.08.31 (일) 23:59`, 오픈 시각 미확정이면 "2026.08.01 (금) 오픈 · 시각 미정" (DB 추가 제안: `races.registration_opens_time_known`). 접수 예정이고 7일 이내면 카운트다운 "오픈까지 2일 4시간" |
| 종목 | 종목별 행: 종목명, 거리, 참가비, 출발 시각, 제한 시간, 정원. 종목별 접수 기간(`race_events.registration_opens_at/closes_at`)이 대회 접수 기간과 다르면 그 종목 행에 "접수 {기간}"을 추가 표시 |
| 코스 | 코스 경로를 지도에 그리는 것은 Phase 2 이후 (`race_courses`). Phase 1은 코스 안내 링크가 있으면 [코스 보기 (공식)] 버튼 (DB 추가 제안: `races.course_url`) |
| 링크 | [공식 홈페이지], [접수하러 가기] (접수 중일 때 강조). 인앱 브라우저. 닫고 돌아오면 조건에 따라 "접수 완료했나요?" 시트 (4.10.1) |
| 출처 | "출처: {source_name} · 최종 확인 {YYYY.MM.DD}" + "대회 정보는 변경될 수 있어요. 정확한 정보는 공식 홈페이지를 확인하세요." (P-RACE-02) |
| 제보 | 하단 텍스트 버튼 "정보가 틀렸나요? 제보하기" → S-024 |
| 하단 고정 바 | [♡ 관심] 토글, [참가 예정 추가] (추가했으면 [참가 예정 · {종목}] → S-023 수정 모드). 참가 예정이면 버튼 아래 작은 글씨로 접수 상태 ("접수 전" 등) |

- 앱에 표시하는 출처는 **공식 홈페이지 또는 주최 측만**이다. 대회 일정 집계 사이트는 내부 발견 경로로만 기록하고 앱에 표시하지 않는다 (집계 사이트 운영자의 서면 허락을 받은 경우에만 "정보 제공: ○○"를 추가). 표시할 출처는 `race_sources.is_primary = true`인 출처다 (tech/04).
- 취소된 대회: 상단에 회색 안내 박스 "이 대회는 취소되었어요." [참가 예정 추가] 비활성. 관심 해제는 가능.
- 연기된 대회: 상단 안내 "이 대회는 연기되었어요. 새 일정은 공식 홈페이지를 확인하세요." 참가 예정 추가 가능.
- 지난 대회(`race_date < 오늘`): [참가 예정 추가] 비활성, 라벨 "종료된 대회". 이미 참가 예정에 추가했으면 "참가한 대회" 표시.
- 공유 버튼은 **Phase 1에 없다** (D-016).

**대회장 위치 지도** (D-008, 지도 SDK는 네이버 지도를 앱 내부 `MapView` 래퍼로 사용)
| 상황 | 표시 |
|---|---|
| 좌표(`venue_point`) 있음 | **미니 지도**: 기본 정보 아래, 가로 꽉 참 × 높이 180pt. 대회장 좌표 중심, 줌 15 (대회장 주변 블록이 보이는 수준). 마커 1개 + 마커 위 장소명 말풍선. 미니 지도는 **제스처 비활성** (화면 스크롤과 충돌 방지). 미니 지도를 탭하면 **전체 화면 지도**. 지도 아래 한 줄: 장소명 · 주소, 오른쪽에 [길찾기] |
| 좌표 없음, 주소 또는 장소명 있음 | 지도 영역 대신 회색 박스: 아이콘 + "지도 위치가 아직 등록되지 않았어요" + 장소명·주소 텍스트 + [주소 복사] + [지도 앱에서 검색] (장소명 또는 주소를 검색어로 지도 앱 열기) |
| 좌표·주소·장소명 모두 없음 | 지도 영역을 숨기고 기본 정보의 장소 행에 "미정 · 공식 홈페이지 확인" |
| 지도 로딩 실패 (SDK 오류, 네트워크) | 미니 지도 자리에 회색 박스 "지도를 불러오지 못했어요" + [다시 시도]. 장소명·주소, [주소 복사], [길찾기]는 그대로 동작 |
| 오프라인 | 지도 대신 회색 박스 "오프라인 상태라 지도를 볼 수 없어요" + 장소 텍스트 (캐시된 지도 타일은 쓰지 않음) |

**전체 화면 지도** (S-022 안의 하위 화면 — 화면 수 24개에 포함하지 않음)
- 구성: 상단 [닫기]·장소명, 지도(이동·확대·축소 제스처 가능), 대회장 마커, 하단 카드(장소명, 주소, [주소 복사], [길찾기]). 지도를 움직인 뒤 [대회장으로] 버튼을 누르면 처음 위치로 돌아간다.
- **내 위치 버튼·현재 위치 표시는 넣지 않는다.** Phase 1 앱은 위치 권한을 요청하지 않는다 (9장, 01 환경 문서의 "필요한 순간에 요청" 원칙).
- 지도 SDK가 제공하는 기본 UI 중 위치 추적 버튼은 끈다. 축척·로고·저작권 표시는 SDK 약관대로 둔다.
- **Phase 1은 다크 모드에서도 기본(밝은) 지도**를 쓴다. 네이버 지도 SDK의 야간 모드는 내비게이션 지도 전용이라 일반 지도에 쓸 수 없다 (개발자 확인). 어두운 커스텀 스타일(NCP 스타일 에디터)은 추가 비용을 확인한 뒤 적용한다 `[확인 필요: 커스텀 스타일 비용]`.
- 전체 화면 지도는 미니 지도와 별도 지도 객체라 진입할 때마다 지도 로드가 1회 더 집계된다고 보고 비용을 잡는다 [추정, 개발 중 NCP 콘솔로 실측].

**[길찾기] 보조 버튼 — 지도 앱 열기**
- 탭하면 선택 시트: **네이버 지도 / 카카오맵 / Apple 지도(iOS) / Google 지도(Android)**. 기기에 설치된 앱만 보여준다 (Apple 지도·Google 지도는 기본 앱이라 항상 표시).
- 선택한 앱을 대회장 좌표 도착지 **도보 길찾기**로 연다 (좌표가 없으면 검색). 도착지 이름·검색어는 장소명, 장소명이 없으면 주소. Google 지도는 국내에서 도보 길찾기가 안 될 수 있어 대중교통으로 연다 [추정]. 앱별 URL은 개발자 handoff `20261021-planner-developer-venue-map-admin-input.md` 답변 2번.
- 마지막으로 고른 앱을 기기에 저장해 다음에는 시트 맨 위에 둔다 (시트는 매번 띄움).
- 앱 열기에 실패하면 네이버 지도 모바일 웹을 인앱 브라우저로 연다.
- [주소 복사]: 주소(없으면 장소명)를 클립보드에 복사, 토스트 "주소를 복사했어요".

- 지도 비용 절감: 미니 지도는 해당 영역이 화면에 들어올 때 불러온다 (지연 로딩). 대회 목록·캘린더·홈에는 지도를 넣지 않는다.

**수용 기준**
- Given 어떤 대회든, Then 상세 화면에 출처와 최종 확인일이 항상 보인다.
- Given 대회 상태 cancelled, Then [참가 예정 추가]가 비활성이고 취소 안내가 보인다.
- Given 접수 중인 대회, When [접수하러 가기], Then `registration_url`이 인앱 브라우저로 열리고 `external_link_opened` 이벤트가 기록된다.
- Given `registration_url`이 없음, Then [접수하러 가기] 버튼이 보이지 않고 [공식 홈페이지]만 보인다.
- Given 좌표가 있는 대회, Then 미니 지도에 대회장 마커가 보이고, 탭하면 전체 화면 지도가 열린다.
- Given 좌표가 없고 주소만 있는 대회, Then 지도 대신 "지도 위치가 아직 등록되지 않았어요"와 [지도 앱에서 검색]이 보인다.
- Given 어떤 경우든, Then 앱이 위치 권한을 요청하지 않는다.
- Given 카카오맵이 설치되지 않은 기기, When [길찾기], Then 선택 시트에 카카오맵이 보이지 않는다.

### 4.8 F-013 관심 대회 등록

**사용자 스토리**
- 러너로서, 나갈지 고민 중인 대회를 저장해 두고 접수 오픈 알림을 받고 싶다.

**상세 동작**
- 하트 버튼(S-020 카드, S-022 하단 바)으로 켜고 끈다. 즉시 반영(낙관적 업데이트), 실패하면 원래 상태로 되돌리고 토스트 "저장하지 못했어요".
- 켤 때 토스트: "관심 대회에 추가했어요. 접수 오픈 전에 알려드릴게요" (접수 예정일 때) / "관심 대회에 추가했어요" (그 외).
- 관심 등록한 사용자는 해당 대회의 N-01~N-03 대상이 된다. 대상은 발송 30분 전에 확정하므로, 그 전에 관심을 해제하면 알림이 가지 않는다 (7.1).
- **참가 예정에 추가하면 관심이 자동으로 켜진다.** 참가 예정인 대회의 관심을 끄려고 하면: "참가 예정인 대회예요. 관심을 해제해도 참가 예정은 유지돼요." [해제] / [취소]. 관심을 해제해도 참가 예정자 알림(N-04~N-06)은 계속 간다.
- 지난 대회·취소 대회에도 관심을 켤 수 있다 (알림은 가지 않음).
- 1인당 관심 대회 최대 **200개**. 초과 시 "관심 대회는 200개까지 저장할 수 있어요. 지난 대회를 정리해주세요".
  - 한도는 **사용자가 하트로 직접 켜는 경우에만** 막는다. 참가 예정 추가로 관심이 자동으로 켜질 때는 200개가 차 있어도 막지 않고 켠다 (201개 이상 가능). 참가 예정이 더 강한 의사 표시이고, 참가 예정 대회가 관심 목록·알림에서 빠지면 혼란스럽기 때문이다. 참가 예정 자체에도 30개 한도가 있어 무한히 늘지 않는다.
  - 200개 이상인 상태에서 하트로 새 관심을 켜면 위 문구로 막는다 (자동으로 켜진 것도 개수에 포함).
- **알림 권한 미결정 상태에서 처음 관심 등록**하면 S-006과 같은 내용의 바텀시트를 1회 띄운다 (6.6).

**수용 기준**
- Given 접수 예정 대회에 관심 등록, When N-01/N-02/N-03 발송 시각이 오면, Then 알림을 받는다 (관심 추가 시점에 이미 지난 시각의 알림은 받지 않는다).
- Given 발송 30분 전보다 먼저 관심 해제, Then 해당 대회의 N-01~N-03을 받지 않는다.
- Given 참가 예정 추가 성공, Then 관심 목록에도 해당 대회가 있다.

### 4.10 F-015 참가 예정

> **용어 (D-019)**: 앱에서 "이 대회 종목에 나간다"고 표시하는 것을 **참가 예정**이라고 부른다 (v1.3까지 "참가 등록"). 실제 대회 접수는 공식 홈페이지에서만 하며, 사용자는 앱에 **접수 상태**(접수 전 / 접수 완료 / 접수 못 함)를 기록한다 (4.10.1). DB 테이블 `race_registrations`와 API 경로의 `registration`은 내부 이름으로 유지할 수 있다 (화면 문구에는 쓰지 않는다).

**용어 선택 근거**
| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **참가 예정** | 일상어, 의도만 표시하고 "접수"를 연상시키지 않음. 이미 S-060·S-061 탭 이름으로 쓰고 있어 화면 간 일관됨. "참가 예정 · 접수 전"처럼 접수 상태와 붙여 읽기 자연스러움 | "예정"이 다소 밋밋함 | **채택** |
| 나갈 대회 | 친근하고 의도가 분명함 | 명사구라 버튼·상태로 쓰기 어색 ("나갈 대회 · 접수 완료", "나갈 대회 해제") | 보류 — 마케팅 문구로 활용 가능 |
| 출전 예정 | 짧고 명확 | "출전"은 선수·엘리트 느낌, 페르소나(지원)에게 거리감. 공식 "출전 확정"과 혼동 여지 | 미채택 |

화면 문구: 버튼 [참가 예정 추가] / 추가된 상태 [참가 예정 · {종목}] / 해제 [참가 예정 해제] / 화면 S-023 제목 "참가 예정 추가" (수정 모드 "참가 예정 수정").

**사용자 스토리**
- 러너로서, "이 대회 하프에 나간다"고 표시하고 목표 기록을 정해 페이스 전략을 받고 싶다.
- (지원) 10K 기록밖에 없지만, 하프 목표를 앱이 추천해주면 좋겠다.
- 러너로서, 공식 홈페이지에서 접수를 마쳤는지 앱에 기록해 두고, 이미 접수한 대회의 마감 알림은 받고 싶지 않다.

**상세 동작**
1. S-022 [참가 예정 추가] → S-023.
2. **종목 선택** (필수, 라디오). 종목이 1개면 자동 선택.
3. **목표 기록** (선택). 세 가지 중 하나:
   - (a) **예측 추천 사용**: 예측 가능한 기록이 있으면 예상 기록과 범위를 보여주고 [이 기록을 목표로] 버튼 → 목표 = 예상 기록 T̂ (초 단위 그대로 저장·표시).
   - (b) **직접 입력**: 시·분·초.
   - (c) **목표 없이 완주**: 목표 기록 없음 (`goal_time_sec = null`).
   - 예측 가능한 기록이 없으면 (a) 자리에 "기록을 입력하면 예상 기록을 추천해드려요" + [기록 입력하기] → S-031 (저장 후 S-023으로 돌아와 입력하던 상태 유지).
   - 종목 거리가 3,000m 미만 또는 42,195m 초과(예: 3km 걷기, 50km)이면 예측 추천 (a)를 보여주지 않고 "이 종목은 예상 기록을 지원하지 않아요" 회색 문구 + (b)(c)만 제공한다. 페이스 전략(S-033)은 목표 기록이 있으면 목표 기준 스플릿만 보여준다.
   - 목표 종목이 풀코스이고 첫 풀코스(5.5)이면 보수적 목표도 함께 제안: "첫 풀코스라면 {T×1.05} 목표를 권해요" [이 기록으로].
3-1. **접수 상태** (필수, 세그먼트): `접수 전` / `접수 완료`. 기본값은 대회 접수 상태에 따라: 접수 예정·접수 중·접수 일정 미정 → `접수 전`, 접수 마감 → `접수 완료` (마감 뒤에 추가하는 사람은 대개 이미 접수한 사람). 아래 도움말 "공식 홈페이지에서 접수를 마쳤다면 접수 완료로 표시해주세요. 마감 알림을 보내지 않아요." `접수 못 함`은 추가 후 S-022·S-061에서만 고를 수 있다 (4.10.1).
4. **목표 기록 검증**: 목표 페이스 **2'50"~15'00"/km** (풀 기준 1:59:33 ~ 10:32:55). 밖이면 "목표 기록을 다시 확인해주세요". 종목 제한 시간(`time_limit_min`)을 넘으면 저장은 되지만 경고 "제한 시간({h:mm})보다 길어요. 완주 인정이 안 될 수 있어요".
5. [추가하기] → 서버 저장 (앱은 화면에서 선택된 접수 상태를 `entryStatus`로 **항상** 보낸다). `goal_pace_sec_per_km`는 서버가 `round(goal_time_sec ÷ (distance_m ÷ 1000))`로 계산해 저장한다.
6. 저장 후:
   - 목표 기록이 있으면 → S-033 (해당 참가 예정 기준 페이스 전략, 예측을 새로 계산해 `race_registration_id`를 연결해 저장).
   - 목표 기록이 없으면 → S-022로 돌아가고 토스트 "참가 예정에 추가했어요".
   - 접수 상태가 `접수 전`이고 대회가 `접수 예정` 또는 `접수 중`이면 1회 바텀시트: "공식 접수는 대회 홈페이지에서 해야 해요. BeRun은 접수를 대신하지 않아요." [접수하러 가기] (접수 중일 때) / [닫기]. "다시 보지 않기" 체크 시 기기에 저장 (P-RACE-01).
7. 관심이 자동으로 켜지고, N-04·N-05 대상이 된다.

**수정·해제**
- S-022 [참가 예정 · {종목}] 또는 S-061에서 S-023 수정 모드로 연다. 수정 모드에도 접수 상태 세그먼트가 있다 (`접수 못 함` 포함 3개).
- 종목 변경: 다른 종목으로 바꾸면 기존 목표 기록을 지우고 "종목이 바뀌어 목표 기록을 다시 정해주세요" 안내 (거리가 같은 종목이면 유지).
- 목표 기록 변경: 언제든.
- [참가 예정 해제] (수정 모드 하단 텍스트 버튼) → 확인 다이얼로그 "참가 예정을 해제할까요? 목표 기록도 함께 지워져요." [해제하기] / [닫기] → `race_registrations` 행 삭제, 연결된 `predictions.race_registration_id`는 null, N-04·N-05 대상에서 빠진다. 관심은 유지.
- 대회일이 지난 참가 예정은 수정·해제할 수 없다 (Phase 4 결과 입력 대상).

**제약**
| 규칙 | 근거 | 처리 |
|---|---|---|
| 한 대회에 한 종목만 | P-VER-04, `UNIQUE (user_id, race_id)` | 이미 참가 예정이면 S-023은 수정 모드로만 열린다 |
| 취소된 대회는 추가 불가 | P-RACE-06 | 버튼 비활성. 서버도 거부 (409) |
| 지난 대회는 추가 불가 | — | 버튼 비활성. 서버도 거부 |
| 1인당 미래 대회 참가 예정 최대 30개 | 어뷰징 방지 | "참가 예정 대회는 30개까지 추가할 수 있어요" |
| 참가 예정은 L0(자가 등록) | P-VER | 인증 기능은 Phase 2 |

**수용 기준**
- Given 하프·10K 종목이 있는 대회, When 하프 선택 + 목표 1:58:00 입력 + [추가하기], Then `race_registrations`에 `goal_time_sec = 7080`, `goal_pace_sec_per_km = 336` (= round(7080 ÷ 21.097))이 저장되고 S-033이 열린다.
- Given 이미 참가 예정인 대회, When 다른 종목으로 새로 추가 시도 (API 직접 호출), Then 서버가 409 `ALREADY_PLANNED`를 반환한다.
- Given 풀 종목, When 목표 1:50:00 입력 (2'36"/km), Then "목표 기록을 다시 확인해주세요"가 뜬다.
- Given 제한 시간 5시간 풀 종목, When 목표 5:20:00, Then 경고가 뜨지만 추가는 된다.
- Given 참가 예정 해제, Then 관심 목록에는 남아 있고 N-04·N-05를 받지 않는다.
- Given 접수 중인 대회, When 접수 상태를 바꾸지 않고 [추가하기], Then `entry_status = not_registered`(접수 전)로 저장된다.

### 4.10.1 접수 상태 기록 (D-019)

**목적**: ① "참가 예정"이 실제 접수가 아님을 분명히 하고 ② 이미 접수한 사람에게 마감 알림을 보내지 않고 ③ Phase 2 페이스 그룹·참가자 통계에서 "실제로 접수한 사람"을 구분할 데이터를 쌓는다. 앱은 실제 접수 여부를 확인할 수 없으므로 **사용자 자기 기록**이다 (참가 인증 P-VER과 별개).

**상태값** (참가 예정 1건당 하나, DB `race_registrations.entry_status`)
| 상태 | 값 | 화면 표시 | 뜻 |
|---|---|---|---|
| 접수 전 | `not_registered` | 배지 `접수 전` | 아직 공식 접수를 하지 않음 (기본값) |
| 접수 완료 | `registered` | 배지 `접수 완료` | 공식 접수(추첨 대회는 신청)를 마침 |
| 접수 못 함 | `missed` | 배지 `접수 못 함` | 마감됐거나 추첨에서 떨어져 이번에는 못 나감 |

- 추첨 대회: 신청을 마쳤으면 `접수 완료`, 떨어졌으면 `접수 못 함`. 상태 선택 시트에 "추첨 대회는 신청을 마쳤으면 접수 완료, 떨어졌으면 접수 못 함으로 바꿔주세요" 안내 (접수 방식이 추첨일 때만).
- 상태는 **대회 당일까지**(`race_date ≥ 오늘`, KST) 언제든 바꿀 수 있다. 대회일 다음 날부터 읽기 전용 (Phase 4 결과 입력 대상). 참가 예정 수정·해제 규칙(4.10)과 같다.
- `접수 못 함`으로 바꾸면 다이얼로그: "이번 대회는 참가 예정에서 뺄까요?" [참가 예정 해제] / [그대로 두기]. 그대로 두면 `지난 대회` 탭으로 갈 때까지 참가 예정 탭에 회색으로 남는다.

**공식 접수 링크에서 돌아왔을 때 묻기 (복귀 질문)**
| 항목 | 규칙 |
|---|---|
| 계기 | S-022에서 [접수하러 가기] 또는 [공식 홈페이지]로 인앱 브라우저를 열었다가 **닫고 S-022로 돌아온 순간** |
| 조건 (모두) | ① 인앱 브라우저에 **10초 이상** 머물렀다 (실수로 연 경우 제외) ② 돌아온 시점의 대회 접수 상태가 `접수 중` 또는 `접수 일정 미정` ③ 이 대회가 참가 예정이 아니거나, 참가 예정이면서 `접수 전` ④ 아래 "횟수 제한"에 걸리지 않음 |
| 표시 | 바텀시트. 제목 "접수 완료했나요?" / 본문 "공식 홈페이지에서 접수를 마쳤다면 기록해두세요. 마감 알림을 보내지 않을게요." / 버튼 [접수 완료했어요] (주) · [아직이에요] / 시트 바깥 탭·아래로 내리기 = 무시 |

| [접수 완료했어요] — 참가 예정 없음 | S-023으로 이동, 제목 "어느 종목에 접수했나요?", 접수 상태 `접수 완료`가 미리 선택됨. S-023에서 그냥 나가면 아무것도 저장하지 않는다 |
| [아직이에요] / 무시 | 아무것도 저장하지 않는다. 같은 대회에 대해 **24시간 동안 다시 묻지 않는다** |
| 횟수 제한 | 같은 대회에 대해 [아직이에요]·무시가 **누적 3회**가 되면 그 대회는 더 이상 묻지 않는다. [접수 완료했어요] 또는 수동 변경이 있으면 이후 묻지 않는다. 제한 기록은 **기기에 저장** (서버 저장 없음, 앱 재설치 시 초기화 허용) |
| 하지 않는 것 | 푸시로 접수 완료 여부를 묻지 않는다 (마감 알림 N-03 본문이 그 역할). 외부 사이트의 접수 성공 여부를 감지하지 않는다 |

### 4.11 F-016 대회 정보 오류 제보

**사용자 스토리**
- 러너로서, 대회 정보가 공식 홈페이지와 다르면 쉽게 알려주고 반영 여부를 알고 싶다.

**입력 항목과 검증**
| 항목 | 필수 | 선택지·규칙 |
|---|---|---|
| 항목 | 필수 | 대회 일시 / 장소 / 종목·거리 / 참가비 / 접수 기간 / 링크 / 취소·연기 / 기타 (`race_reports.field`: `date`, `venue`, `events`, `fee`, `registration`, `links`, `status`, `other`) |
| 내용 | 필수 | 10~500자. placeholder "어떤 정보가 어떻게 다른지 알려주세요. 근거 링크가 있으면 함께 적어주세요." |

**상세 동작**
- [제보하기] → 서버 저장 (`status = open`) → 토스트 "제보해주셔서 감사해요. 확인 후 알려드릴게요" → S-022.
- 제한: 같은 대회 하루 3건, 전체 하루 10건. 초과 시 "오늘은 더 제보할 수 없어요. 내일 다시 시도해주세요".
- 처리 결과는 N-07 (앱 내 알림 목록에만, 푸시 없음).
- 사진 첨부는 Phase 1에서 제외.
- 지난 대회·취소된 대회도 제보 가능.

**수용 기준**
- Given 내용 9자, Then [제보하기]가 비활성이다.
- Given 같은 대회에 오늘 3건 제보함, When 4번째 제보, Then 서버가 429를 반환하고 안내 문구가 뜬다.
- Given 관리자가 "반영" 처리, Then 제보자의 S-011에 N-07(반영)이 생긴다.

### 4.12 F-020 기록 예측

**사용자 스토리**
- 러너로서, 내 최근 기록으로 목표 거리의 현실적인 예상 기록 범위와 신뢰도를 알고 싶다.

**상세 동작** (계산 규칙은 5장)

## 5. 기록 예측 알고리즘 (F-020, F-021) — 수치 확정

> 모델 버전: **`riegel-1.06-v1`**. 모든 상수는 서버 설정값으로 두고, 바꾸면 모델 버전을 올린다. 계산은 서버에서만 한다 (앱은 표시만).

### 5.1 입력 기록 조건 (eligible)
| 조건 | 값 |
|---|---|
| 거리 | 3,000m ≤ 거리 ≤ 42,195m |
| 날짜 | 예측일 기준 0~365일 전 (`days_ago = 예측일 − run_date`) |
| 기록 | 4.4의 페이스 범위 검증을 통과한 기록 (저장된 기록은 모두 통과) |

### 5.2 기록별 환산과 가중치
각 기록 i (거리 D1, 기록 T1)를 목표 거리 D2로 환산한다.

**Riegel 식:** `T2_i = T1_i × (D2 / D1_i) ^ 1.06`

**거리 비율:** `r_i = max(D1_i, D2) / min(D1_i, D2)` (항상 ≥ 1)

**가중치:** `w_i = w_최신성 × w_거리 × w_종류`

| 최신성 (`days_ago`) | w_최신성 | | 거리 비율 `r` | w_거리 | | 종류 | w_종류 |
|---|---|---|---|---|---|---|---|
| 0 ~ 90일 | 1.0 | | r ≤ 1.2 | 1.0 | | 대회 (`race`) | 1.0 |
| 91 ~ 180일 | 0.7 | | 1.2 < r ≤ 2.2 | 0.8 | | 개인 훈련 (`training`) | 0.8 |
| 181 ~ 365일 | 0.4 | | 2.2 < r ≤ 4.3 | 0.5 | | | |
| | | | r > 4.3 | 0.25 | | | |

참고 거리 비율: 5K↔10K 2.0, 10K↔하프 2.11, 하프↔풀 2.0, 5K↔하프 4.22, 10K↔풀 4.22, 5K↔풀 8.44.

**자동 선택:** 가중치 내림차순 상위 **5개** (동점이면 최근 기록 → 긴 거리 순). 사용자가 직접 고르면 고른 기록 전부(최대 5개)를 같은 가중치로 계산한다.

### 5.3 예상 기록 (점 추정)
`T̂ = Σ(w_i × T2_i) / Σ w_i` → **초 단위 반올림**. 이후 모든 계산은 반올림한 T̂로 한다.

**분산 (변동계수):** 사용 기록이 2개 이상일 때
`CV = sqrt( Σ w_i × (T2_i − T̂)² / Σ w_i ) / T̂` (1개면 CV = 0)

### 5.4 신뢰도
먼저 **낮음** 조건을 본다. 하나라도 해당하면 낮음.
| # | 낮음 조건 |
|---|---|
| L1 | 사용 기록 중 가장 작은 거리 비율 `r_min > 4.3` (예: 5K → 풀, 5K → 하프 단독) |
| L2 | 목표가 풀(D2 ≥ 42,000m)인데 사용 기록 중 **하프 이상(D1 ≥ 21,000m) 기록이 없음** |
| L3 | 사용 기록이 **모두** 180일보다 오래됨 |
| L4 | `CV > 6%` (기록 간 차이가 큼) |

낮음이 아니면서 아래를 **모두** 만족하면 **높음**, 나머지는 **보통**.
| # | 높음 조건 |
|---|---|
| H1 | `r ≤ 2.2`이면서 180일 이내인 기록이 1개 이상 |
| H2 | 사용 기록 2개 이상 |
| H3 | `CV ≤ 3%` |

**신뢰도 사유 문구** (S-033 배지 아래, 해당하는 첫 번째 사유 1개):
| 신뢰도 | 사유 | 문구 |
|---|---|---|
| 높음 | — | "목표 거리와 비슷한 최근 기록이 여러 개 있어 비교적 믿을 만해요." |
| 보통 | 기록 1개 | "기록이 1개뿐이에요. 기록을 더 넣으면 정확해져요." |
| 보통 | H1 불충족 | "목표 거리와 차이가 있는 기록으로 계산했어요." |
| 보통 | CV 3~6% | "기록 간 차이가 조금 있어요." |
| 낮음 | L1·L2 | "목표 거리보다 훨씬 짧은 기록으로 계산했어요. 장거리 훈련으로 실제 기록을 확인해보세요." (P-PRED-03) |
| 낮음 | L3 | "최근 6개월 안의 기록이 없어요. 현재 실력과 차이가 클 수 있어요." |
| 낮음 | L4 | "기록 간 차이가 커서 범위를 넓게 잡았어요." |

### 5.5 범위 계산
| 신뢰도 | 빠른 쪽 (하한) | 느린 쪽 (상한) |
|---|---|---|
| 높음 | T̂ × (1 − 0.02) | T̂ × (1 + 0.03) |
| 보통 | T̂ × (1 − 0.03) | T̂ × (1 + 0.06) |
| 낮음 | T̂ × (1 − 0.05) | T̂ × (1 + 0.10) |

- 느린 쪽을 더 넓게 잡는다 (Riegel은 장거리, 특히 풀코스에서 낙관적으로 나오는 경향이 있음).
- **반올림**: 목표 ≥ 21,000m → 하한은 **분 단위 내림**, 상한은 **분 단위 올림**, 표시 `h:mm`. 목표 < 21,000m → **10초 단위** 내림/올림, 표시 `mm:ss`.
- 예상 기록 T̂는 초 단위 그대로 `h:mm:ss`로 표시한다.
- **평균 페이스** = `round(T̂ ÷ (D2 ÷ 1000))` 초/km.

**첫 풀코스 보수 목표 (P-PRED-04, +5% 확정):**
- 조건: 목표가 풀이고, 사용자의 **전체 기록(기간 무관)** 에 42,000m 이상 기록이 없음.
- 제안값 = `T̂ × 1.05` → **분 단위 올림**. 문구: "첫 풀코스라면 {제안값} 목표를 권해요. 후반 30km 이후를 대비해 여유를 두세요."

**대회 제한 시간 경고:** 참가 대회 기준 예측이고 상한 > `time_limit_min × 60`이면 "예상 범위가 제한 시간({h:mm})에 가까워요."

### 5.6 구간 스플릿 (F-021)
- 구간 단위: 목표 거리 < 15,000m → **1km**, ≥ 15,000m → **5km**. 마지막 행은 결승(목표 거리). 예: 하프 = 5, 10, 15, 20, 21.1km.
- 기준 기록 T, 거리 D, 평균 페이스 p = T ÷ D (초/m).
- **이븐 페이스**: 지점 x의 누적 = `p × x`.
- **네거티브 스플릿**: 전반(0 ~ D/2) 페이스 `p × (1 + 0.015)`, 후반(D/2 ~ D) 페이스 `p × (1 − 0.015)`. 총 기록은 T와 같다. 반환점을 포함한 구간은 두 페이스를 거리 비율로 섞는다.
  - 지점 x ≤ D/2: 누적 = `x × p × 1.015`
  - 지점 x > D/2: 누적 = `(D/2) × p × 1.015 + (x − D/2) × p × 0.985`
- 누적 시각은 초 단위 반올림, 페이스는 초/km 정수 반올림해 표시한다.
- 결과는 `predictions.splits`에 `{even: [...], negative: [...]}`로 저장한다.

### 5.7 예시 계산 (검증용 — 테스트 케이스로 그대로 사용)

> 예측일 = 2026-10-21. 소수는 계산 과정 표시용이며 서버는 부동소수점으로 계산 후 마지막에만 반올림한다.

#### 예시 1 — 지원: 10K 기록 3개 → 하프 (신뢰도 높음)
| 기록 | D1 | T1 | days_ago | 종류 | r | T2 (초) | w |
|---|---|---|---|---|---|---|---|
| A | 10,000 | 55:00 (3300) | 60 | 대회 | 2.110 | 7280.9 | 1.0 × 0.8 × 1.0 = 0.80 |
| B | 10,000 | 56:30 (3390) | 150 | 대회 | 2.110 | 7479.5 | 0.7 × 0.8 × 1.0 = 0.56 |
| C | 10,000 | 57:10 (3430) | 300 | 대회 | 2.110 | 7567.8 | 0.4 × 0.8 × 1.0 = 0.32 |

- T̂ = (0.80×7280.9 + 0.56×7479.5 + 0.32×7567.8) / 1.68 = 12435.0 / 1.68 = 7401.8 → **7402초 = 2:03:22**
- CV = 1.61% → L1~L4 해당 없음. H1(A: r 2.11, 60일) ✓, H2(3개) ✓, H3(1.61% ≤ 3%) ✓ → **신뢰도 높음**
- 범위: 7402 × 0.98 = 7254.0 → 내림 **2:00** / 7402 × 1.03 = 7624.1 → 올림 **2:08** → **2:00 ~ 2:08**
- 평균 페이스: 7402 / 21.097 = 350.9 → **5'51"/km**
- 스플릿 (5km 단위)
  | 지점 | 이븐 누적 | 네거티브 누적 |
  |---|---|---|
  | 5km | 0:29:14 | 0:29:41 |
  | 10km | 0:58:29 | 0:59:21 |
  | 15km | 1:27:43 | 1:28:15 |
  | 20km | 1:56:57 | 1:57:03 |
  | 21.1km | 2:03:22 | 2:03:22 |
  - 네거티브: 전반 5'56"/km (356.1초), 후반 5'46"/km (345.6초)
- 해석: 지원의 "하프 2시간 안에" 목표는 범위 하한(2:00)에 걸린다. S-023에서 1:59:59를 직접 입력하는 것은 허용되며(페이스 범위 내), 별도 경고는 없다.

#### 예시 2 — 경민: 하프·풀·10K 훈련 → 풀 (신뢰도 높음, 기록 섞임)
| 기록 | D1 | T1 | days_ago | 종류 | r | T2 (초) | w |
|---|---|---|---|---|---|---|---|
| A | 21,097 | 1:27:30 (5250) | 45 | 대회 | 2.000 | 10946.2 | 1.0 × 0.8 × 1.0 = 0.80 |
| B | 42,195 | 3:08:20 (11300) | 120 | 대회 | 1.000 | 11300.0 | 0.7 × 1.0 × 1.0 = 0.70 |
| C | 10,000 | 40:10 (2410) | 30 | 훈련 | 4.220 | 11086.5 | 1.0 × 0.5 × 0.8 = 0.40 |

- T̂ = (0.80×10946.2 + 0.70×11300.0 + 0.40×11086.5) / 1.90 = 21101.5 / 1.90 = 11106.1 → **11106초 = 3:05:06**
- CV = 1.42%. L2: 하프 이상 기록 있음 ✓(해당 없음). H1(A: r 2.0, 45일) ✓, H2 ✓, H3 ✓ → **신뢰도 높음**
- 범위: 11106 × 0.98 = 10883.9 → 내림 **3:01** / 11106 × 1.03 = 11439.2 → 올림 **3:11** → **3:01 ~ 3:11**
- 평균 페이스: 11106 / 42.195 = 263.2 → **4'23"/km**
- 첫 풀코스 아님 (B가 42,195m) → 보수 목표 제안 없음.
- 스플릿 (5km 단위, 일부): 이븐 5km 0:21:56 · 20km 1:27:44 · 40km 2:55:28 · 42.2km 3:05:06 / 네거티브 5km 0:22:16 · 20km 1:29:03 · 40km 2:55:37 · 42.2km 3:05:06 (전반 4'27"/km, 후반 4'19"/km)
- 해석: 서브3(3:00:00)는 범위 밖(하한 3:01). 목표 2:59:59 직접 입력은 허용된다.

#### 예시 3 — 첫 풀 도전: 5K 훈련 기록 1개 → 풀 (신뢰도 낮음)
| 기록 | D1 | T1 | days_ago | 종류 | r | T2 (초) | w |
|---|---|---|---|---|---|---|---|
| A | 5,000 | 25:00 (1500) | 20 | 훈련 | 8.439 | 14386.7 | 1.0 × 0.25 × 0.8 = 0.20 |

- T̂ = 14386.7 → **14387초 = 3:59:47**
- L1(r_min 8.44 > 4.3) ✓, L2(하프 이상 기록 없음) ✓ → **신뢰도 낮음**, 사유 "목표 거리보다 훨씬 짧은 기록으로 계산했어요. 장거리 훈련으로…"
- 범위: 14387 × 0.95 = 13667.6 → 내림 **3:47** / 14387 × 1.10 = 15825.7 → 올림 **4:24** → **3:47 ~ 4:24**
- 평균 페이스: 14387 / 42.195 = 341.0 → **5'41"/km**

### 6.8 S-011 알림 목록

### 6.14 S-030 기록 홈 (기록 탭 루트)
- **구성**
  1. [기록 예측하기] 큰 버튼 → S-032.
  2. **최근 예측**: 최근 3개 `predictions` 카드 (목표 거리, 예상 기록, 범위, 신뢰도, 날짜, 연결된 대회명). 예측 이후 기록이 추가·수정·삭제됐으면 "기록이 바뀌었어요 · 다시 예측" 링크. 탭 → S-033 (저장된 결과 그대로 표시). 3개 넘으면 [전체 보기] → 예측 목록(같은 카드 리스트, 최근 50개). 예측 0개면 섹션 숨김.

### 6.16 S-032 기록 예측

- **이동**: [예측하기] → S-033 / 진입 시 참가 대회에서 왔으면 목표 거리 미리 선택됨.

### 6.17 S-033 예측 결과 · 페이스 전략
- **구성 (위에서 아래)**
  1. 목표: "하프 (21.1km)" 또는 "{대회명} 하프".
  2. 결과 카드: 예상 기록 `2:03:22` (크게), 범위 "2:00 ~ 2:08", 평균 페이스, 신뢰도 배지(높음 초록 / 보통 노랑 / 낮음 회색) + 사유 문구 (5.4).
  3. **면책 문구 (P-PRED-01, 항상)**: 결과 카드 바로 아래 회색 박스. "예상 기록은 통계적 추정이며 훈련 상태, 코스, 날씨, 컨디션에 따라 달라질 수 있습니다. 무리한 목표 설정은 부상의 원인이 될 수 있습니다."
  4. 첫 풀 보수 목표 카드 (해당 시), 제한 시간 경고 (해당 시).
  5. 사용한 기록 (접기/펼치기): 기록별 거리·기록·날짜·환산 기록.
  6. 페이스 전략 (4.13): 기준 토글(목표/예측), 탭(이븐/네거티브), 스플릿 표.
  7. 하단 버튼: 참가 대회 기준이면 [이 기록을 목표로 설정] (목표 = 예상 기록, 확인 다이얼로그 없이 저장 + 토스트 "목표 기록을 {h:mm:ss}로 정했어요"), 아니면 [이 거리 대회 찾기] → S-020 (거리 필터 적용). 공통 [다시 예측] → S-032.
- **상태**: 저장된 예측을 열면 계산 없이 표시. 연결된 참가 예정이 해제됐으면 대회명 대신 거리만 표시.
- **기록이 바뀐 뒤 열 때** (S-030 카드·참가 예정 기준[홈 [페이스 전략 보기], N-04, S-061] 모두): 저장된 예측을 **자동으로 다시 계산하지 않는다** — 사용자가 보던 숫자가 말없이 바뀌지 않게. 대신 결과 카드 바로 위에 안내 줄 "기록이 바뀌었어요 · 다시 예측"을 표시하고, 탭하면 S-032를 같은 목표(참가 예정이면 그 참가 예정, 아니면 같은 거리)가 선택된 상태로 연다. 다시 예측해 저장하면 그 참가 예정의 최신 예측이 되어 이후에는 새 값이 보인다 (API `recordsChangedSince`).
- **참가 예정 기준으로 열었는데 예측을 만들 수 없을 때** (홈 [페이스 전략 보기], N-04/N-05, S-023 저장 후 — `GET /registrations/{id}/strategy`의 `prediction = null`):
  - 목표 기록 있음: 결과 카드 자리에 "기록을 넣으면 예상 기록도 볼 수 있어요" + [기록 추가] → S-031 (사유가 미지원 거리면 "이 종목은 예상 기록을 지원하지 않아요", 버튼 없음). 페이스 전략은 **목표 기준 스플릿만** 표시하고 기준 토글은 숨긴다. 면책 문구는 예측 결과가 없으므로 표시하지 않는다.
  - 목표 기록 없음: 빈 상태 "목표 기록이나 최근 기록이 있어야 페이스 전략을 만들 수 있어요" + [목표 기록 정하기] → S-023 수정 모드 + [기록 추가] → S-031.
  - 로딩: 결과 카드·스플릿 표 스켈레톤.
- **이동**: 뒤로 → 진입 화면.

## 7. 알림 상세

### 7.1 발송 규칙
| 규칙 | 내용 |
|---|---|
| 채널 | 푸시 + 앱 내 알림 목록(`notifications`). N-07은 앱 내만 |
| 시간대 | KST. 서비스 알림(N-01~N-07)은 야간에도 발송한다 (사용자가 관심 등록으로 요청한 정보). 마케팅(N-08 광고)은 **08:00~20:59에만** (P-NOTI-02) |
| 예약 방식 | **대회 단위 예약표**(`notification_schedules`)를 대회 저장 시 계산한다 (사용자별 예약을 미리 만들지 않음). 발송 30분 전에 그 시점의 대상(관심 ∪ 참가 예정)을 조회해 사용자별 알림을 확정하고, 정해진 시각에 발송한다. 따라서 대상 확정 전에 관심을 해제하면 가지 않고, 추가 시점에 이미 지난 알림은 생기지 않는다 |
| 재계산 | 관리자가 접수 시각·대회일·출발 시각을 바꾸면 그 대회의 미발송 예약표를 다시 계산한다 |
| 종목별 접수 기간 | 접수 알림(N-01~N-03)과 접수 상태 배지는 **대회 단위** 접수 기간(`races`)을 기준으로 한다. 종목별 기간만 있고 대회 기간이 비어 있으면 종목 중 가장 이른 오픈·가장 늦은 마감을 대회 기간으로 본다. 참가 예정자에게 N-03은 참가 예정 종목의 마감 시각을 쓴다 |
| 발송 직전 확인 | ① 사용자 알림 설정 ② 대회 상태 (취소면 N-01~N-05 취소) ③ 대상 조건 (관심·참가 여부가 아직 유효한지) ④ 시각 조건 (예: 접수가 이미 열렸으면 N-01 취소) |
| 중복 방지 | `(user_id, race_id, kind, scheduled_at)` 기준 1건 |
| 묶음 발송 | 같은 사용자에게 같은 종류·같은 예약 시각 알림이 2건 이상이면 푸시는 1건으로 묶는다 ("내일 접수가 시작되는 관심 대회 3개"). 앱 내 목록에는 대회별로 각각 남긴다. 묶음 푸시를 탭하면 S-011로 이동 (개발자 확인: 가능) |
| 묶음 문구 | 제목은 아래 표, 본문은 대회명을 ", "로 이어 60자 안에 넣고 넘치면 "외 n개"로 끝낸다 (예: "2027 서울마라톤, 2026 춘천마라톤 외 2개"). 탭하면 S-011 |
| 늦은 발송 (워커 장애·재시작) | 문구가 사실과 달라지면 보내지 않고 `cancelled`로 둔다. 유효 구간: N-01 오픈 **전날(KST)까지** / N-02 오픈 **시각 전까지** (시각 미정이면 오픈일 23:59까지) / N-03 마감 **전날까지** / N-04 **D-7 당일(KST) 23:59까지** / N-05 **대회 전날까지** / N-06 **대회일까지**(지난 대회의 변경 알림은 보내지 않음). 정상 운영에서는 영향 없음. 취소 건수는 A-002 실패 수와 별도로 로그 |
| 휴면 계정 | 휴면(`dormant`) 계정에는 서비스·마케팅 푸시와 앱 내 알림을 만들지 않는다 (P-RET-03). **예외: N-06a·b·c(대회 취소·연기·일정 변경)는 휴면 계정에도 푸시 + 앱 내 알림으로 보낸다** — 사용자가 직접 저장한 대회의 취소·일정 변경은 환불·일정 확인과 관련될 수 있어 받지 못하면 손해가 생길 수 있기 때문. BeRun이 환불 주체는 아니며(P-RACE-01) 이 알림은 법정 고지가 아니라 서비스 안내다. 휴면 계정 개인정보를 분리 보관해야 하는 경우 이 예외가 가능한지 `[확인 필요]` (P-RET-03) |
| 실패 처리 | 푸시 발송 실패 시 1분 간격 최대 3회 재시도. 그래도 실패하면 앱 내 알림만 남기고 실패 로그 (A-002 집계) |
| 무효 토큰 | 플랫폼이 토큰 무효를 응답하면 `devices.push_token` 삭제 |
| 보존 | 앱 내 알림은 90일 후 파기 (P-RET 추가) |

### 7.2 알림 목록과 문구 초안

> `{}`는 변수. **제목 최대 30자, 본문 최대 60자** (코드포인트 기준). 길이가 넘치면 **대회명만** 줄인다: 대회명 최대 길이 = 상한 − 고정 문구 길이, 줄일 때는 끝에 "…"(1자로 셈)를 붙인다. 예: N-01 제목 고정 문구 "내일 ··· 접수가 시작돼요" 12자 → 대회명 최대 18자("…" 포함). N-03 고정 12자 → 18자. 모든 제목의 대회명 자리는 18자 이상 남도록 문구를 정했다. (v1.6까지의 "대회명 20자" 규칙은 폐기 — 30자 제한과 충돌)
> N-06a·b 제목은 조사(이/가) 처리를 피하려고 "{대회명} 대회가 …" 형태로 쓴다.

> 기술: Next.js (tech/02), `admin.berun.app` [미정]. PC 브라우저 전용 (가로 1280px 이상). 모든 쓰기 작업은 `admin_audit_logs`에 남긴다.

#### 8.4.3 종목 일괄 추가
- 종목 영역은 **표(그리드)** 다. 한 행 = 종목 하나. 셀 사이는 Tab / Enter로 이동, 행 삭제는 행 끝 [×].
- 프리셋 버튼: [5K] [10K] [하프] [풀] [기타] — 누르면 행 추가. 종목명(`5K` / `10K` / `하프코스` / `풀코스`), 분류, 거리(5,000 / 10,000 / 21,097 / 42,195)가 채워진다. 여러 개를 연달아 눌러 한 번에 추가. [하프+풀], [5K+10K+하프+풀] 묶음 버튼도 둔다.
- **공통값 적용** 줄: 표 위에 출발 시각 / 제한 시간 / 참가비 입력란과 [모든 종목에 적용]. 입력한 칸만 모든 행에 덮어쓴다. 이후 행별로 고칠 수 있다.
- 제한 시간 칸이 비어 있으면 분류별 참고값을 회색 placeholder로 보여준다 (5K 60분, 10K 90분, 하프 180분, 풀 300분). placeholder는 저장되지 않는다 — 공식 정보를 확인한 값만 저장한다.
- 거리를 직접 고치면 분류를 3.3 기준으로 다시 제안한다 (사용자가 분류를 직접 바꿨으면 유지).

#### 8.4.4 복제 입력
- [복제] → 원본의 모든 필드를 복사한 **새 초안**을 열고 상단에 "{원본 대회명}을 복제했어요" 표시.
- 날짜 자동 이동: 대회일·접수 오픈·접수 마감·출발 시각을 **+1년, 같은 요일에 가장 가까운 날짜 = +364일(52주)** 로 옮긴다 (윤년이어도 364일이 항상 가장 가깝다. 예: 2026-11-08 (일) → 2027-11-07 (일)). 옮긴 날짜 칸은 노란 배경으로 강조해 확인을 유도한다. 원본 대회일이 오늘 이후면 날짜를 옮기지 않는다 (같은 시즌 다른 대회 복제용).
- 대회명의 연도 표기(`2026`)는 새 대회일 연도로 바꾼다. 회차 표기(`제23회`)는 +1 한다.
- 복사하지 않는 것: 상태(예정으로), 게시 상태(초안으로), 최종 확인일(비움 — 게시 전에 반드시 확인), 출처 확인 일시(비움), 관심·참가 예정, 제보.
- 복제 원본 id는 감사 로그에 남긴다.

**저장 시 동작**
- 같은 대회명 + 같은 대회일이 있으면 경고 "같은 대회가 이미 있어요" (저장은 가능).
- 게시 상태에서 아래 항목을 바꾸면 확인 모달: "관심 {n}명, 참가 예정 {m}명에게 영향이 있어요."
  - 상태 → 취소: N-06a 자동 발송 (끌 수 없음)
  - 상태 → 연기: N-06b 자동 발송
  - 대회일·출발 시각·접수 기간 변경: 알림 예약 재계산 (자동) + [변경 알림 보내기] 체크 시 N-06c 발송 (기본 체크)
- 게시 → 초안 되돌리기는 관심·참가 예정이 0일 때만 가능.
- **삭제**는 관심·참가 예정이 0이고 owner일 때만. 그 외에는 "취소" 상태로 바꾼다 (P-RACE-06).
- 주최 측 삭제·수정 요청(P-RACE-04)은 Phase 1에서 **고객센터 이메일**로 받고, 이 화면에서 처리(삭제 대신 `숨김` 가능)한 뒤 감사 로그 메모에 "주최 측 요청"을 남긴다. 주최사 셀프 등록·수정 폼은 Phase 2.
- 수집기가 찾은 신규·변경 후보(`race_candidates`, tech/05)는 관리자 검수 후에만 `races`에 반영한다. 후보 검수 화면은 개발자 설계(tech/05)를 따른다.

**CSV 일괄 등록**: Phase 1에서는 하지 않는다 (사람이 공식 홈페이지를 확인하며 입력하는 것이 원칙, D-013). 데이터 확보는 빠른 입력(8.4.1) + 수집기 후보 검수(tech/05)로 한다.

### 8.5 A-004 대회 정보 오류 제보 처리
- **목록**: 상태(미처리 / 반영 / 반려), 접수 시각 오래된 순, 72시간 경과 강조. 열: 대회명, 항목, 내용 앞 50자, 접수 시각, 상태.
- **상세**: 제보 내용 전문, 제보자 닉네임(탈퇴했으면 "탈퇴한 사용자"), 대회 현재 값(제보 항목 강조), 같은 대회의 다른 미처리 제보.
- **처리**
  - [반영]: A-003 수정 폼이 새 탭으로 열림 → 저장 후 제보 화면에서 [반영 완료] → `status = applied`, N-07a 발송.
  - [반려]: 사유 템플릿 선택 (공식 정보와 같아요 / 근거를 확인할 수 없어요 / 이미 반영되어 있어요 / 기타 직접 입력 0~100자) → `status = rejected`, N-07b 발송. (DB 추가 제안: `race_reports.resolution_note`, `resolved_at`, `resolved_by`)
  - 같은 대회의 같은 항목 제보를 한 번에 처리 (일괄 반영/반려) — 각 제보자에게 각각 알림.

| 발송 시각 | 즉시 / 예약. 마케팅은 08:00~20:59 밖이면 저장 불가 |
| 테스트 발송 | 관리자 본인의 테스트 계정(사용자 id 입력)으로 1건 |
| 승인 | operator가 작성하면 owner가 [발송 승인] 해야 발송/예약된다. **owner가 작성하면 승인 단계 없이** 발송 전 확인 모달(대상 수, 미리보기)만 거친다 (Phase 1은 owner 1인 운영, D-014) |

- 앱 내 공지 목록 화면은 Phase 1에 따로 두지 않는다. 공지는 S-011 알림 목록에 N-08a(또는 N-08b)로 들어가고 탭하면 **공지 상세 화면**(S-011의 하위 화면, 화면 수 미포함)을 연다. 구성: 제목, 게시일, 본문(일반 텍스트, 줄바꿈 유지, URL은 자동 링크 → 인앱 브라우저), 하단에 이동 대상 버튼(대회 보기 / 대회 목록). **웹뷰·공지 웹 페이지는 쓰지 않는다** — 웹 도메인이 필요 없고 내린 공지(`withdraw`)는 "내려간 공지예요"로 바로 반영된다.
